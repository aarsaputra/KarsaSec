## 1. System Architecture & Component Inventory

`sast-scan` is an open-source static analysis orchestration wrapper designed to execute multiple external specialized static analysis engines (e.g., Bandit, Semgrep, PMD, Gitleaks, Psalm, GoSec, SpotBugs, NodeJSScan) against a target project directory, normalize their outputs into SARIF (Static Analysis Results Interchange Format v2.1.0), and aggregate/deduplicate findings.

```text
Target Source Code
        │
        ▼
CLI Entry Point (`scan`) ───► Project Type Detection (`lib/context.py`)
        │
        ▼
Scanner Selection & Command Dispatch (`lib/executor.py`)
   ├──► Tool A (Bandit / Python)  ──► JSON/Text Output
   ├──► Tool B (Semgrep / Generic) ──► JSON Output
   ├──► Tool C (PMD / Java)        ──► XML Output
   └──► Tool D (Gitleaks / Secret) ──► JSON Output
        │
        ▼
Format Converter (`lib/convert.py`) ──► Individual SARIF Reports
        │
        ▼
Result Aggregator & Deduplicator (`lib/aggregate.py`)
        │
        ▼
Unified SARIF Report (`reports/sast-scan-report.sarif`) & Summary
```

### Key Source Modules
- `scan`: Main CLI driver, argument parsing, execution pipeline setup.
- `lib/context.py`: Language and framework auto-detection routines.
- `lib/executor.py` (`exec_tool`, `execute_default_cmd`): Subprocess launcher, environment configuration (`JAVA_HOME`, PATH), and output suppression logic.
- `lib/convert.py`: Parser adapters converting native tool outputs (JSON, XML, CSV, text) into standard SARIF format.
- `lib/aggregate.py`: Inter-tool result aggregation, line-range mapping, and fingerprint-based deduplication.
- `lib/config.py`: Hardcoded tool execution flags, default arguments, and rule purpose mappings.

## 2. Rule Engine & Analysis Model

`sast-scan` itself **does not implement an internal rule engine, AST parser, or dataflow engine**. It relies entirely on delegating analysis to backend static analyzers:
- **Rule Representation**: External (Tool-specific YAML, XML, Python rules).
- **Matching Model**: Delegated entirely to downstream binaries.
- **Candidate Definition**: A raw finding string or JSON dictionary produced by an executed binary stdout/report file.

---

## 3. False Positive & Qualification Architecture

`sast-scan` has **no semantic qualification layer**. It operates purely as a post-processing aggregator:

1. **Suppression**: Based on tool-level suppression annotations (e.g. inline comments `# nosec`, `// noinspection`) which are handled natively by the backend tools, or global exclusion regexes passed to sub-tools.
2. **Deduplication (`lib/aggregate.py`)**:
   - `aggregate.py` groups findings by matching `(file_path, line_number, rule_id)`.
   - Fingerprints are generated by hashing normalized rule IDs and file locations.
3. **Severity Normalization (`lib/convert.py`)**: Maps tool-specific severities (e.g. `HIGH`, `ERROR`, `WARNING`, `INFO`, `CRITICAL`) to standard SARIF levels (`error`, `warning`, `note`).

## 4. Architectural Lessons for KarsaSec

### Patterns KarsaSec SHOULD Consider
- **Standardized Finding Normalization**: Normalizing external or multi-pass candidates into a strict, unified intermediate representation (like KarsaSec's `CandidateFinding` -> `QualifiedFinding`) ensures consistency regardless of detection source.
- **Unified SARIF Reporting**: Standardizing output schema to SARIF v2.1.0 facilitates integration with CI/CD platforms and GitHub Security code scanning.

### Patterns KarsaSec SHOULD NOT Copy
- **Subprocess Tool Wrapping without Structural AST Context**: Delegating static analysis to external CLI tools without shared AST/IR context creates huge precision loss, duplicate findings, and inability to trace dataflow across boundaries.
- **Syntactic Text-Based Deduplication**: Merging findings strictly by line numbers or regex rule IDs ignores semantic correlation and evidence context.
